## 1. Project in one paragraph

**Floor Mop** is a Python data-gathering, filtration and monitoring pipeline for newly launched Solana meme tokens. It detects launch/pool events, enriches each candidate, filters out garbage (especially honeypots), monitors survivors at adjustable tick speeds, and emits a stream of structured records. It is the upstream half of **Sylvester Solone** (Hermes agent brain + public TypeScript MCP server + Jupiter execution). Floor Mop has **no wallet, no keys, no authority, and no limits of any kind**. It is a data stream. Whatever consumes the stream (Hermes) and whatever constrains execution belong to the Sylvester roadmap.

**Trading thesis it serves:** find tokens offering a 20%+ exit. Catching a rug early enough to sell into its own spike is acceptable. Tokens showing sustainable interest may be held longer. The load-bearing question for any candidate is **"can the position be exited at all?"** (honeypot/sellability), more than "will it pump?"

**Target readiness:** before meme season around the spring 2028 Bitcoin halving.

### 3.2 Configuration loader — `src/floor_mop/config.py`

**What it does:** `load_settings(config_dir=None, env=None) -> Settings` merges three layers, later winning, dicts deep-merged:

1. `config/default.toml` — **required**, committed, holds every default.
2. `config/local.toml` — optional, **gitignored**, personal overrides.
3. Environment variables prefixed `FLOOR_MOP__` (double underscore). Prefix stripped, split on `__`, lowercased into a nested key path. Example: `FLOOR_MOP__LOGGING__LEVEL=DEBUG` sets `logging.level`.

Config directory resolution: `config_dir` argument, then `FLOOR_MOP_CONFIG_DIR` (single underscore, **not** an override), then `./config`.

**Models** (pydantic v2, `extra="forbid"`, `frozen=True`, **no field defaults in code**): `Settings(logging: LoggingConfig, paths: PathsConfig)`.

- `LoggingConfig`: `level` (DEBUG/INFO/WARNING/ERROR/CRITICAL), `dir` (Path), `max_bytes` (PositiveInt), `backup_count` (NonNegativeInt), `console` (bool)
- `PathsConfig`: `data_dir` (Path)

**Current `config/default.toml` placeholder values** (all to be tuned in session): `level="INFO"`, `dir="logs"`, `max_bytes=10485760` (10 MiB), `backup_count=5`, `console=true`, `data_dir="data"`.

**Design decisions and why:**

- **Pydantic, not stdlib dataclasses:** typed validation, clear errors, same models will serialise records later.
- **Plain `pydantic`, not `pydantic-settings`:** pydantic-settings handles layered TOML + env awkwardly. A short hand-written merge gives exact control over precedence.
- **No code defaults:** enforces the project rule that nothing tunable is a literal in source. Defaults live only in `default.toml`.
- **`extra="forbid"` everywhere:** typos in TOML or env fail loudly instead of being silently ignored.
- **The loader does not create directories or resolve paths.** Consumers (e.g. logging) do that.
- **No import-time reads, no global singleton.**

**Security bug found and fixed (important lesson):**

- The agent's first self-test checked that a secret did not appear in the exception **message**, and passed. But `raise ConfigError(...) from exc` made Python print the chained pydantic error beneath it, which includes `input_value='<the secret>'`. A real run with `FLOOR_MOP__LOGGING__LEVEL=hunter2-secret` printed the secret.
- **Fix:** every wrapped raise uses `from None`, and the validation-error formatter reports only field location and pydantic message text, never the input.
- **Regression tests** (in `test_config.py`) assert the secret is absent from `str(exc)` **and** from `"".join(traceback.format_exception(exc))`, plus `exc.__cause__ is None` and `exc.__suppress_context__ is True`.
- The user pushed that fix before the post-fix real-shell leak check was pasted; the regression tests were what later confirmed it closed.

### 3.5 Application logging — `src/floor_mop/logging_setup.py`

**Public API:** `setup_logging(settings) -> logging.Logger`, `teardown_logging() -> None`, `JsonLineFormatter`, constants `LOGGER_NAME = "floor_mop"` and `LOG_FILENAME = "floor_mop.log"`.

**Behaviour:**

- Configures only the `floor_mop` logger. **Never** touches the root logger, never calls `basicConfig`, never changes `propagate`.
- **File handler:** `RotatingFileHandler` writing **JSON lines** to `<logging.dir>/floor_mop.log`. One object per physical line, keys in order: `ts` (UTC ISO 8601 with milliseconds and `Z`), `level`, `logger`, `msg`, then `exc` (only if an exception is attached), then `extra` (only if `extra=` was passed). Serialised with `default=str` so unserialisable extras never crash logging.
- **Console handler:** optional (`logging.console`), writes to `sys.stderr` resolved at call time, human-readable, UTC timestamps.
- **Creates the log directory itself** (`parents=True, exist_ok=True`), because the config loader deliberately does not.
- **Idempotent:** installed handlers carry a private marker; each `setup_logging` call removes and closes marked handlers, then installs fresh ones. Unmarked handlers are never touched.
- **Fails fast:** `OSError` from directory creation or file opening propagates. A bad log path stops startup rather than running with no logs. Verified manually: `FLOOR_MOP__LOGGING__DIR=/dev/null/cannot-create` raises `NotADirectoryError`, exit status 1.
- **No import-time side effects.**
- `teardown_logging()` exists mainly so tests and shutdown code can release file handles (Windows cannot delete open files).

**Scope boundary:** this is **application** logging (operational messages) only. **Record persistence** (storing candidate records and the raw event corpus) is a separate, later task that depends on the schema and the storage backend.

**Design decision:** stdlib `logging` with a ~20-line custom formatter, not structlog or loguru. No new dependency and no second logging idiom for a collaborator to learn. Revisit only if needs outgrow it.

**Manual verification performed by the user (all passed):** one line per record and valid JSON with no duplicate handlers after two setup calls; rotation produced exactly `floor_mop.log`, `.1`, `.2` and no `.3`, each under the cap (452 bytes with `max_bytes=512`, which is normal because rotation fires before a write would cross the cap); bad log path fails loudly.

### 3.6 Logging tests — `tests/test_logging_setup.py`

27 tests covering directory creation, JSON validity and key order, UTC timestamps, level filtering, console on/off and UTC, idempotence and replacement (including a changed directory), exception and extra fields, single-line guarantee for newline/unicode, rotation and `backup_count` (including 0), teardown and file-handle release, survival of unmarked handlers, root-logger and `propagate` isolation, fail-fast `OSError` with no half-installed handlers, and import-time side effects (via subprocess). Tests do not depend on the module's private marker name. An autouse fixture tears down logging around every test.

**Test totals at last report: 51 passed** (24 config + 27 logging). Ruff clean. Three consecutive runs of the logging suite gave identical results.

## 6. Where things stand and what comes next

**Phase 0 final state:** scaffold, config loader (24 tests), logging module (27 tests), 51 tests passing, all pushed.

**Next phase: Phase 1 — Data Source Survey.** Per the roadmap (and the user's priority): after scaffolding, find data sources potentially better than Helius RPC webhooks, exploring many options.

- **Candidates named by the user or roadmap:** Helius (webhook, WebSocket and Geyser/gRPC as three separate candidates), Raydium, Pump.fun, GMGN, Jito, Birdeye, direct or provider-hosted Geyser, others to be identified.
- **Evaluation axes:** measured latency (time from on-chain event to Floor Mop having it), coverage (what share of launches, which venues missed), cost (including under load), reliability, rate limits, data richness.
- **Outputs:** a written comparison with measured numbers, a chosen primary feed plus at least one fallback, and a thin adapter interface so sources are swappable.
- **Suggested handling:** planning the survey is research and brainstorming, so start in `MODE: CHAT`. Move to `MODE: DEV` for measurement scripts. Latency scripts should be throwaway or kept in a separate directory; nothing in `src/` should come out of the survey except the adapter interface.
- **Immediately after the survey:** the record schema and "hit" definition, designed together with the adapter's normalised event shape.

**Design intent for the schema (proposed, not agreed):** append-only stage records (detection, enrichment, filtration, monitoring snapshot), each with its own `schema_version`, `candidate_id`, `stage`, and three timezone-aware UTC timestamps (occurred, received, processed); the feed's `raw` payload kept as an opaque blob; enrichment results carrying an explicit ok/failed/not-run status so "sellability unknown" can never be mistaken for "sellable"; amounts as raw integers plus decimals, never floats; filter verdicts carrying reject reasons (rule, observed value, threshold) and the filter config version. Storage-agnostic pydantic models serialising to JSON lines. Monitoring time-series and simulator outcomes left to Phases 5 and 6.

**Optional cleanup still available:** the `requires-python` fix, a README, and a review pass over `config.py` and `logging_setup.py` (the architect has not read either file; their behaviour is known only from specs, agent reports, tests and manual checks).

## 8. Phase 6 caution carried forward

A "what would have happened" simulator is easy to write and easy to make optimistic. A credible one models fill delay between signal and landing, price impact against real pool depth at intended size, fees including failed transactions, and exit slippage (usually worse than entry on a falling token). It must also track outcomes for **rejected** candidates, otherwise a too-strict filter is indistinguishable from a good one. Phase 6 already showed signs of scope creep; its scope is to be pinned down before implementation begins.
